# deyehomePVsystem

Локален сайт за мониторинг на домашната фотоволтаична система (Deye SUN-15K-SG01HP3-EU-AM2, 34 панела, 8 × BOS-G ~40.96 kWh): събиране на данните от Deye Cloud API, дългосрочно съхранение, KPI дашборди, бенчмаркове и цели (окупаемост, оползотворяване на енергията).

**Приложението само чете данни. То никога не променя настройки на инвертора или батерията.**

## Тайни

Данните за достъп се пазят само в локален `.env` (в `.gitignore`). Шаблон: [.env.example](.env.example).

## Първа проверка на достъпа (етап 0)

Нужен е само Python 3.10+, без допълнителни пакети:

```bash
cp .env.example .env      # попълни DEYE_EMAIL, DEYE_PASSWORD, DEYE_APP_ID, DEYE_APP_SECRET
python3 -m collector.probe
```

Скриптът взима токен, списък на станциите и устройствата, последните стойности, вчерашните 5-минутни данни и списъка с точки (measure points) на инвертора и батерията. Записва ги в `data/probe/` (извън git). Клиентът допуска само четящи endpoint-и; тестът `python3 -m unittest discover -s tests -t .` проверява това.

## Колектор и база данни (етап 1)

Колекторът тегли данните от Deye Cloud и ги пише в SQLite файла `data/pv.sqlite`. Схемата е в [migrations/](migrations/) и се прилага сама при старт. Описание: [docs/04-database.md](docs/04-database.md).

### С Docker (препоръчително за постоянна работа)

```bash
cp .env.example .env      # попълни данните за достъп
docker compose up -d --build
docker compose logs -f collector
```

При първо пускане колекторът изтегля цялата история, която Deye още пази (5-минутни кадри на станцията от 03.12.2025, дневни и месечни суми, точките на инвертора за последните ~90 дни). След това пита на 5–7 минути. Базата е в `./data` на хоста.

### Без Docker

Нужен е само Python 3.10+ (без външни пакети):

```bash
python3 -m collector.main backfill   # еднократно: цялата налична история
python3 -m collector.main run        # непрекъснат режим (прави backfill, ако не е правен)
python3 -m collector.main poll       # само един цикъл
python3 -m collector.main check      # изчислената енергия срещу дневните суми и броячите на Deye
python3 -m collector.main external   # PVGIS и облъчване от Open-Meteo (в режим run се пуска само веднъж в час)
python3 -m collector.main rebuild    # преизчисли 5-минутната, часовата и дневната енергия от кадрите
python3 -m collector.main import-invoices invoices/   # фактурите на Електрохолд (PDF): показания, суми, тарифи
python3 -m collector.main import-invoices seed/electrohold-invoices.json   # всички 46 фактури 12.2022–10.2026, вече прочетени
```

За фактурите е нужен `pdftotext` (пакет `poppler-utils`; в Docker образа е включен). Сложи PDF-ите в папка `invoices/` (извън git) и в Docker пусни `docker compose run --rm collector python -m collector.main import-invoices /invoices`.

### Какво прави един цикъл

1. `/device/latest`: всички ~100 точки на инвертора; кадърът се пази веднъж, по времето на логера (`collectionTime`). Ако от предишния кадър са минали повече от ~8.5 минути, липсващите кадри се допълват от `/device/history`.
2. `/station/history/power` за последния час: 5-минутните кадри на станцията (PV, товар, мрежа, батерия, SOC). От тях се смята енергията за всеки 5-минутен интервал, после за часа и деня.
3. Веднъж на ден след 01:00: дневните и месечните суми на Deye за сверка и настройките на батерията, режима и TOU (само четене; пазят се при промяна).

## Дашборд (етап 2)

Сайтът чете локалната база `data/pv.sqlite` и никога не говори с Deye; пише само ръчните данни (цели, сценарии, параметри, тарифи, CAPEX/OPEX, фактури). Описание на страниците и сметките: [docs/05-dashboard.md](docs/05-dashboard.md).

### С Docker

`docker compose up -d --build` пуска и колектора, и сайта. Сайтът е на `http://<компютъра>:8088` в домашната мрежа (на същия компютър `http://localhost:8088`). Друг порт: `WEB_PORT=...` в `.env`. Отвън, на постоянен адрес (Tailscale Funnel без домейн или Cloudflare Tunnel с домейн): описание в [docs/08-public-access.md](docs/08-public-access.md).

### Без Docker

```bash
pip install -r requirements-web.txt
uvicorn web.app:app --host 0.0.0.0 --port 8088   # DB_PATH=... ако базата не е в data/pv.sqlite
```

Страници: Обзор, Производство (вкл. инвертора), Батерия, Потребление и мрежа, Икономика, Качество на данните, Здраве (състояние, натоварване, температури и прогноза за износването), Цели (цели, сценарии, бизнес план и бенчмаркове; редактират се от сайта). API: `/api/kpi?from=ГГГГ-ММ-ДД&to=ГГГГ-ММ-ДД`, `/api/series`, `/api/power?day=`, `/api/inverter?day=`, `/api/payback`, `/api/invoices`, `/api/catalog`, `/api/goals`, `/api/health`; пълен списък на `/api/docs`.

Тестове: `python3 -m unittest discover -s tests -t .` (тестовете на сайта се пропускат, ако FastAPI не е инсталиран).

## Архив, наблюдение и защита (след одита от 10.2026)

Услугата `guard` в Docker Compose (`python3 -m collector.guard run`) не говори с Deye и не получава данните за достъп до него:

- **Архив:** всеки ден след `BACKUP_HOUR` (по подразбиране 03:00) прави консистентно копие на базата (`VACUUM INTO` + `PRAGMA quick_check`), компресира го като `pv-ГГГГ-ММ-ДД.sqlite.gz` в папката `BACKUP_DIR` и пази последните 7 дни, 8 недели и 12 месеца. За копие извън компютъра `BACKUP_DIR` да сочи синхронизирана папка (например iCloud Drive). Преди всяка миграция на съществуваща база се прави и копие до нея (`pv.pre-NNN-*.sqlite`, пазят се последните три). Ръчно: `python3 -m collector.guard backup`.
- **Наблюдение:** на всеки 5 минути проверява дали идват кадри (над `STALE_MINUTES`, по подразбиране 45 мин = проблем), дали Deye връща само грешки, дали архивът е от последните 30 часа, мястото на диска, дали сайтът отговаря и, ако е настроен, дали адресът отвън (Tailscale Funnel или Cloudflare Tunnel) работи. Проблемите се виждат в лентата долу вляво на всяка страница и в „Качество на данните“; известие се праща при промяна и на всеки `ALERT_REPEAT_HOURS` часа, докато трае, по Telegram, имейл или ntfy, ако са попълнени в `.env` (виж `.env.example`).
- **Защита при запис:** сайтът приема промени само от собствените си страници (проверка на `Origin`/`Referer` и само JSON или PDF), така че чужда страница в браузъра не може да промени нищо. С `WRITE_PASSWORD` в `.env` промените искат и парола веднъж на браузър (бисквитка за 180 дни); четенето остава свободно.
